Reproduce a workload

Use an isolated application environment outside the source checkouts. PyCBC requires its normal build dependencies, including LALSuite. CPU and CUDA application environments may be separate; select their interpreters explicitly. The dated runtime manifest records observed versions and extension hashes. A new build records its own hashes rather than claiming byte identity with the measured runtime.

git clone https://github.com/xangma/pycbc.git sources/candidate
git -C sources/candidate checkout --detach jax-benchmark-2026-10-09
git clone https://github.com/xangma/pycbc.git sources/original
git -C sources/original checkout --detach jax-benchmark-original-2026-10-09
python tools/prepare_inputs.py plan

Follow the input recipe to fetch and verify the public frames and bank XML and regenerate the exact bank files. The input-generation checkout and environment are separately pinned. Install/build each benchmark source in its matching application environment. Keep the source checkout clean; ignored native extensions are hashed before and after execution.

The native-command runner uses only the Python standard library. It launches one excluded prime per arm, then at least three fresh processes in rotated arm order, followed by a separate profile when configured. Each arm gets private caches and temporary directories. Scientific/backend selectors come from the manifest; inherited PyCBC/JAX settings are cleared. Source imports, exact input hashes, return codes, deadlines and descendant cleanup are checked. Resolved receipts remain private because they contain paths, commands and process IDs.

python -m pycbc_jax_benchmarks run campaigns/inspiral-1536-four-arm.json \
    --sources sources --inputs inputs --output results/four-arm \
    --python original-cpu="$CPU_PYTHON" --python branch-cpu="$CPU_PYTHON" \
    --python jax-cpu="$JAX_CPU_PYTHON" --python cuda="$CUDA_PYTHON" --plan

Set those interpreter variables to your installed runtimes. Add --cpus ARM=IDs for each arm to choose physical-core-aware affinity for your hardware. Inspect --plan, then omit it to execute into a new output directory. The plan checks source/input hashes and does not import or launch the applications. Diagnostic manifests for Inspiral and Live define the corresponding smaller measurement campaigns. Their work.expected values are contracts to check, not observed completion evidence.

The general runner measures native CLI launch through exit and log closure. It excludes source/input guards and preflight imports. It does not reproduce the dated observer timings or named profile windows, which include passive observers, in-process checks, final synchronization and Live suffix accounting. Use the archived controllers for those boundaries. Profiling and unprofiled samples are always separate.

Successful execution leaves scientific qualification, completed warm-up, verified work and realtime capacity marked unavailable. Validate them using the protocol before making a performance claim. The four-arm manifest is a reproducible starting point, not evidence that those four arms have already passed.

Publish a new campaign

Freeze a new source revision, input hashes, manifest and protocol version before running. Keep failed runs and unmet gates explicit. Publish a new dated directory and release; do not overwrite an earlier campaign. A PR should cite the release, name the exact relevant workload and timing scope, and state qualification limits. A full-stack result must not be described as an individual PR's measured speedup.

Raw Nsight/SQLite captures and bank/frame data are not distributed here. The portable profile data preserve exact selected application intervals and their independent checks without private metadata.
